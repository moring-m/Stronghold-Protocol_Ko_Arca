# 캐시 로딩 지연 점검

## 대용량 캐시의 목록 조회 오류 후속 수정

실사용 브라우저에서 `Cache.keys(): Operation too large`가 발생했다. 앞서 미리보기 로더에 적용한 전체 키 일괄 조회는 대용량 캐시에서 브라우저 응답 크기 제한을 넘을 수 있었다. 이를 제거하고, 이미 알고 있는 리소스 경로를 `CacheStorage.match(path)`로 최대 6개씩 확인하도록 수정했다. 조회 중에도 파일 수·용량 진행도를 표시하며 저장된 파일은 삭제하지 않는다. 30,631개가 모두 캐시에 있는 조건에서 대용량 `Cache.keys()`를 호출하지 않고 다운로드 0회로 완료되는 회귀 테스트를 추가했다. 아래의 일괄 키 조회 시간은 이전 구현에 대한 측정 기록이다.

## 확인된 원인과 수정

배포용 `public/resource-worker.js`의 준비 루프가 파일 하나를 처리할 때마다 전체 리소스 경로 배열을 다시 만들었다. 파일이 약 3만 개일 때 전체 경로 배열 생성도 약 3만 번 반복되는 구조였다. 경로 배열을 작업 묶음마다 한 번 만들도록 변경했다. 네트워크 요청이 전혀 없는 모의 CacheStorage 조건에서 동일한 실제 워커 코드를 실행해 비교했다.

| 조건 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 캐시에 존재하는 파일 30,000개 | 14,379ms | 2,678ms |
| 캐시 조회 호출 | 32,340회 | 32,340회 |
| 작업 묶음 | 469회 | 469회 |
| 이미지 네트워크 요청 | 0회 | 0회 |

이는 자바스크립트 및 준비 루프의 통제된 비교이며 사용자 브라우저의 실제 디스크 성능 측정값은 아니다. 실제 CacheStorage를 사용하는 브라우저의 별도 3,000개 파일 점검에서는 미리보기 로더의 일괄 키 조회가 약 159ms, 완료 표시가 있는 재방문은 약 6ms였고 파일 요청은 0회였다. 미리보기와 배포용 로더는 서로 다른 코드이므로 수치를 혼용하지 않는다.

`public/js/audio.js`는 재생을 위해 캐시에서 읽은 음성도 다시 `cache.put`하고 있었다. 기존 응답을 그대로 읽었을 때는 다시 쓰지 않도록 수정했다. 캐시된 음성 재생에서 다운로드와 쓰기가 모두 0회인지 회귀 테스트로 확인했다.

이전에 발견한 파일별 80ms 대기와 캐시된 음원의 전투 중 대기는 제거된 상태다. 준비 중인 모델의 이미지 디코딩과 Spine 파싱은 파일 저장 여부와 별개다. 실제 모델 하나의 브라우저 측정에서는 약 587KB를 캐시에서 읽는 데 4.6ms, 이미지 디코딩 3.4ms, 모델 준비 71.2ms가 걸렸다. 현재 대기석·상점·배치 유닛을 먼저 준비하며, 전투 중 전체 모델 파싱을 밀어 넣지 않는다.

## 다운로드와 캐시 확인 구분

PNG 복구 후 배포 목록은 30,591개다. 목록에 기록된 파일 크기를 분류하면 다음과 같다. 저장 시의 브라우저 부가 비용은 포함하지 않는다.

| 분류 | 개수 | 크기 |
| --- | ---: | ---: |
| 음성·효과음 | 9,047 | 310,490,134바이트 |
| 추가 스킨 모델 | 2,201 | 350,403,535바이트 |
| 기타 이미지·모델·리소스 | 5,116 | 494,422,460바이트 |

전체 다운로드 기능은 유지한다. 파일이 모두 저장되지 않았다면 진행 바에는 캐시 확인뿐 아니라 실제 다운로드도 포함된다. WebP 사용은 요청에 따라 되돌렸으며 기존 PNG와 에셋 미러를 사용한다.

CacheStorage는 사이트 출처별로 분리된다. 임시 공유 링크의 도메인이 바뀌면 이전 링크나 운영 사이트에 저장한 캐시를 사용할 수 없다. 사용자의 특정 시점에 남은 파일 수와 네트워크 속도는 사용자 브라우저의 측정값 없이 확정할 수 없다.

메인 화면은 전체 캐시 준비를 기다리지 않는다. 현재 UI 자동 검증은 설정 응답이나 워커 설치를 의도적으로 멈춘 조건에서도 메인 화면 조작이 가능한지 확인한다. 화면 하단 진행 바는 백그라운드 작업을 표시하며 파일 수와 바이트 비율을 혼합하지 않는다.
